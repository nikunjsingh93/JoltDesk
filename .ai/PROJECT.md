# JoltDesk project knowledge

## Overview

JoltDesk is an independent desktop workspace for local and remote AI model APIs. It uses the bundled Pi-Bolt coding agent and supports multiple chats and projects, streaming reasoning and code, optional web search and page reading, and file actions in the sidebar.

## Architecture

| Component | Role |
| --- | --- |
| `desktop.cjs` and `desktop-profile.cjs` | Electron lifecycle, profile selection, OS-encrypted credentials, window icon, and desktop file actions |
| `server.mjs` and `rpc.mjs` | Loopback Express/WebSocket server and isolated Pi-Bolt RPC processes, one per chat |
| `connections.mjs` | API normalization, model discovery, context estimates, and model-specific reasoning controls |
| `approval.ts` | App-owned Pi-Bolt extension for permissions, web tool registration, and provider timing |
| `web-tools.cjs` | Public web search and read-only HTML/text extraction |
| `checkpoints.mjs`, `public/changes-panel.mjs`, `public/diff.mjs` | Per-request file checkpoints, restore, Myers line diff, and the Changes tab |
| `git.mjs`, `public/git-panel.mjs` | Git status, HEAD and working-tree file contents, selective commit, push, and the Git tab |
| `terminal.mjs`, `public/terminal-panel.mjs` | Terminal tab: user commands per chat, and live mirrors of the agent's command tools |
| `skills.mjs`, `public/skills-panel.mjs` | Skill discovery, validation, create, import, and remove; the Settings and Files tab UI; and `/` suggestions in the composer |
| `public/instructions.mjs` | Instruction-file list in the Files tab and personal instructions in Settings |
| `public/side-panel.mjs` | Files, Changes, Git, Terminal, and Browser tabs of the shared right panel. The tabs wrap to two rows when the panel is narrow |
| `browser-agent.cjs` | Agent browser actions: numbered-element snapshots, click, type, keys, scroll, screenshot, and agent URL rules |
| `browser-pane.cjs`, `desktop-preload.cjs`, `public/browser-panel.mjs` | Built-in browser: `WebContentsView` tabs owned by the main process, a preload bridge limited to the app origin, and the Browser tab of the right side panel |
| `public/` | HTML, CSS and vanilla JavaScript renderer, including chat state and reply metrics |
| `engine-updater.mjs` and `bundle-engine.mjs` | Verified engine downloads, activation and packaging |
| `test/` | Backend and Electron UI checks with simulated model APIs, plus an opt-in live discovery check |

The Electron window connects to the local server. API and WebSocket calls use the instance token and loopback origin checks. Each chat’s RPC child binds to its own connection and model configuration. UI state, session files, and diagnostics live on disk. There is no database. Desktop credentials are stored separately using Electron safe storage. Browser mode keeps credentials in process memory.

## Development commands

```sh
npm ci
npm start
npm test
npm run build:ui
npm run bundle:engine
npm run zip -- --arm64
```

`npm start` opens Electron. `npm run web` serves the browser UI. `npm test` runs backend tests. UI checks can be run directly, for example `node test/live-stream-ui-check.mjs`. Set `BOLT_TEST_PACKAGED=1` for checks that support the packaged Windows app. Set `BOLT_TEST_BASE_URL` and, if needed, `BOLT_TEST_API_KEY` for `node test/live-api-check.mjs`. That check reads model metadata without generation. Test artifacts go under ignored `work/`.

## Durable decisions and pitfalls

- The supported release target is Windows ARM64. Electron is ARM64. The bundled upstream Windows x64 Pi-Bolt engine runs under Windows emulation. Verify both the packaged app and the embedded engine before releasing.
- The JoltDesk rename keeps the old Windows app ID and opens existing Bolt Desktop data in place. Keeping the existing profile directory also keeps its encrypted credential store together. Fresh installations use `joltdesk`.
- The Windows portable build registers the outer executable as its taskbar relaunch command and icon source before showing the window. Its temporary Electron executable is removed on exit. Pins made before this fix need to be recreated.
- Saved connection identity matters. Distinct APIs can expose the same model ID, so keep model selection, keys, and active requests scoped to their chat’s endpoint.
- Keep thinking effort, thinking budget, and total output limits separate. Qwen3.6 provides On/Off, while Qwen3.8 can expose distinct efforts. A supported Splash connection can enforce a per-request thinking budget. Unsloth Studio exposes a GGUF model-load budget, and the OpenAI-compatible route tested during development did not honor the attempted per-request budget.
- Some servers return the resident model’s properties for every model query. Match the reported model identity before applying those properties.
- Keep streamed scroll containers mounted. Replacing the thinking or code node on each update reset spinner animation, focus, and scroll position. Follow new output only when the reader is already at the bottom.
- Prefer native generation timings where available. Buffered stream chunks can make receipt-based throughput estimates misleading.
- File permissions control the agent’s available tools and approval flow. Approved shell tools run with the current OS user’s permissions. Web access is separately opt-in and reads public pages without running their scripts.
- The built-in browser's pages are native `WebContentsView`s drawn over `#browser-viewport` and above all HTML. The renderer hides them while any `<dialog>` is open, while the side panel shows Files, and when a page fails to load so the error text is visible. Window captures from `BrowserWindow.capturePage()` do not include these views. Capture the view's own `webContents` instead.
- Browser tabs use the `persist:joltdesk-browser` partition, a sandbox, no preload, HTTP(S)-only navigation, and deny-by-default permissions. Agent `browser_open` accepts only public addresses through the same check as `browse_page`. `browser_read` reads the active tab in an isolated world and requires the chat's Web toggle. The user can browse anywhere, including localhost.
- Files, Changes, and Browser share the right side panel. Each tab remembers its own width.
- Checkpoints: in `approval.ts`, the `tool_call` handler snapshots the exact file bytes as base64 after approval and before `write` or `edit` runs. It sends them as a `BOLT_SNAPSHOT:` notification. Run the snapshot only after approval, so declined calls record nothing. The server opens a checkpoint for each prompt in `rpc.turn` and closes it on `agent_settled`, on the handled disposition, on a prompt error, or when the engine closes. Closing records the after-state and drops files that did not change. Paths are absolute, resolved like the tool does from the chat's working directory. Store bytes, not decoded text, so restores are exact for any encoding.
- Restoring a request also restores later requests that touched the same files. It compares each file with the last recorded after-state and returns `needsConfirmation` with conflicts instead of overwriting outside edits. After a restore, the next prompt first sends `/bolt-note`, a hidden custom message, so the model knows. The chat renderer ignores custom messages.
- `git.mjs` runs the `git` CLI with `--literal-pathspecs`, `GIT_TERMINAL_PROMPT=0`, and porcelain v1 `-z` status. Paths are relative to the repository root, so run commands from the root. Commits stage the chosen paths with `--pathspec-from-file`. Do not pass a rename's old path or a staged deletion to `git add`, because they are no longer in the index and `add` fails. Then commit with `--only` for the same paths, so other staged work is left alone. A first commit, with no HEAD yet, cannot use `--only`. `git diff` does not accept `--pathspec-from-file`. Mutations are serialized per repository.
- `oneShot()` in `server.mjs` sends a single tool-free prompt to the chat's model through a temporary Pi-Bolt process. It uses the chat's runner agent directory and a throwaway session in `<data>/one-shot`, so nothing enters the conversation. The Git tab uses it for commit messages.
- Instruction files, verified with the engine: Pi-Bolt reads AGENTS.md from its agent folder (`PI_CODING_AGENT_DIR`, which is per chat at `<data>/runners/<chat>/agent`), then one file per folder from the filesystem root down to the chat's folder. In each folder it reads AGENTS.md, or CLAUDE.md only when AGENTS.md is absent. `defaultProjectTrust: 'never'` does not block them. Personal instructions (`meta.instructions`) are written to that per-chat AGENTS.md when the runner starts. `meta.instructionsRevision` makes `runner()` quietly replace an idle engine before its next use. Closing runners directly would broadcast `engine_closed` and show an error toast.
- The terminal runs each command as its own process without a pseudo-terminal: `pwsh.exe` or `powershell.exe -NoProfile -Command` on Windows, or `$SHELL -c` elsewhere, with `NO_COLOR` and `TERM=dumb`. Stopping uses `taskkill /T /F` on Windows and kills the process group elsewhere. `cd` is handled by the app. Agent commands are mirrored from `tool_execution_start`, `tool_execution_update` (whose `partialResult` holds all output so far), and `tool_execution_end` (`structuredContent.exit_code`). Entries live in memory, up to 40 per chat and 200 KB of output each.
- UI checks that use a folder under `work/` must set `GIT_CEILING_DIRECTORIES`, or Git finds the JoltDesk checkout.
- Attachment paths: the desktop preload uses Electron `webUtils.getPathForFile`; the server accepts an original path only after checking regular-file size and SHA-256 against the upload. Otherwise it saves a copy under `<chat cwd>/attachments/<chatId>/`; per-chat directories let `archiveChat()` move only that chat’s copies to trash. Original files are never archived. The chip shows the source folder or “saved copy”; the copy path is assigned when the prompt is sent.
- Deleting a chat and removing a project share `archiveChat()` in `server.mjs`. It writes a tombstone to `deletedChatIds`, stops the runner, moves session files, metrics, and checkpoints into `<data>/trash/<chatId>`, and closes the chat's terminal. `DELETE /api/projects/:id` refuses while any of the project's chats is running or opening, and it moves only app-created attachment copies out of the project folder.
- Skills, verified with the engine: JoltDesk keeps `--no-skills`, which turns off the engine's own discovery, and passes `--skill <dir>` for each active skill. Explicit paths still load. The engine lists skills for automatic use only when the `read` tool is active, so Chat only mode supports only explicit `/skill:name`. The RPC `prompt` command expands `/skill:name args`, and `get_commands` lists skills. The active set is personal skills (`<data>/skills`) plus project skills when `project.skillsEnabled`, minus `meta.disabledSkills` and invalid or duplicate names. The first name wins, matching the engine. `runner()` compares `rpc.skillKey` and quietly replaces an idle engine when the set changes.
- UI checks launch `test/ui-shell.cjs`, which uses a profile under `BOLT_DATA_DIR`. A shared profile leaked saved panel tabs and widths between checks and made resize-drag steps fail intermittently. Startup buttons (`data-startup`) stay disabled until `app.js` has attached handlers and loaded the workspace, so early clicks are never lost.
- A chat must open even when its API is offline or removed. `openChat` treats a failed `/connections/:id/activate` or a missing saved connection as `offline` (kind `api` or `removed`) instead of throwing. `/history` falls back to `savedMessages()`, which follows the latest branch of the session JSONL by `parentId`, when `runner()` fails, and returns `offline.kind: 'engine'`. The socket's `levels` request ignores runner failures. The model picker selects `connectionId::model` for a chat bound to a non-active API, so choosing any model moves the chat to that API.
- Local browser tools are available in Read/Ask/Bypass even with Web off. In that state browser actions may inspect local files only; the desktop browser agent checks the active URL after navigation as well as before actions. Web search and web pages still require Web. The permission notice directs the model to use browser tools, and attachment prompts identify the exact absolute file path. Browser click/type/press retain their approval behavior.
- Reply duration is measured across the whole user turn from server prompt acceptance, including model requests, tools, and approvals; generation rate and token count remain per assistant message. `turnElapsedMs` carries the monotonic duration to live/reopened UI state, while saved reply metrics preserve it. Older saved metrics cannot reconstruct unrecorded tool wait time. Prompt Copy/Edit controls use the original prompt text; Edit loads a new composer draft rather than rewriting history and asks for reattachment of files.
- Agent browser actions run page code in isolated world 1999. `snapshotPage` stores the numbered elements in `window.__joltRefs` in that world, so page scripts cannot read or forge them, and the numbers go stale after navigation. Input uses `webContents.sendInputEvent` for clicks and keys, and `insertText` for typing, so pages receive trusted events. The browser panel is revealed first, because `capturePage` returns an empty image for a detached view. Password fields are refused. Click, type, and press need one approval per chat in `approval.ts` unless the mode is bypass. `browser_open` allows public URLs, loopback hosts on any port, and local files only when the chat mode is not chat. The internal route passes `allowFiles`. `BOLT_TEST_HOOKS=1` exposes `global.__joltBrowserPane` for `test/browser-actions-ui-check.mjs` only.
- Unsloth Studio reports runtime context at `/v1/status` (`context_length`, plus `model_identifier` and `active_model`). It requires the API key. `studioContextFor` applies the value only to the model it names. `refreshStudioContext` in `server.mjs` runs after a runner starts and after each reply. It saves confirmed values and bumps the profile revision, so the engine restarts with the right window. It also broadcasts `config_changed`. An estimated window (`contextWindowEstimated`) is never shown in the UI.
- Unsloth Studio does not mark image input in `/v1/models`. Discovery uses `capabilities`, `/v1/status` `is_vision` for the loaded model, `/api/models/check-vision/{id}` (tried both encoded and as a plain path), and, last, a `VL` name match. `refreshStudioContext` also updates `input` from `is_vision`. The composer refuses images for a text-only model before sending and keeps the draft. The server check remains.
- Model-loading status: while an identified Unsloth Studio model waits for its first token, `watchStudioLoading` polls authenticated `/api/inference/status` and shows “Loading model…” only if its `loading` list names that model. An unavailable or older endpoint falls back to the ordinary request label. Prompt progress and streamed output take precedence; each poll checks the active request after awaiting the response. This endpoint is distinct from `/v1/status` and may vary by Studio version.
- Prompt progress: for local connections with a llama.cpp profile, `approval.ts` adds `return_progress: true` next to `timings_per_token`. It forwards `prompt_progress` counters (total, cache, processed, time_ms) from `provider_stream_event` as `BOLT_PROGRESS`. The engine delivers chunks with empty `choices` to extensions. The server broadcasts `prompt_progress` until the first delta. The UI shows it while no text has arrived (`!chars`). Do not test `streaming.placeholder`, because `message_start` arrives before the first progress chunk. Unsloth Studio's API description does not mention `return_progress`, so whether it forwards the field is unverified against a live Studio. `watchStudioContext` polls `/v1/status` every 3 s while the first token is pending, until the limit is confirmed.
- Streaming tool arguments other than `write` are rendered with `readableArguments()`, a tolerant formatter for partial JSON.
- Startup: `startServer` must not await API discovery. It loads the active profile's saved models, sets `connected`, and runs `connectionModels` in the background (`startupRefresh`). The result applies only if the active connection and revision are unchanged and no switch is in progress. It does not take the `changeConnection` lock, because that would make user switches fail. `config.refreshing` tells the UI to poll `/config` until the refresh is done. Before this change, an auto-connect to a busy Unsloth server delayed window creation by seconds and showed a black window.
- Releases ship only `JoltDesk-<version>-win-arm64.zip` (`npm run zip -- --arm64`), the unpacked app folder with `JoltDesk.exe`. The user asked to drop the portable exe and the installer after 0.14.0. The old portable target (electron-builder NSIS portable) extracted about 160 MB to TEMP on every launch, and Defender scanned it. A measured run took 27 s before the app process started, against about 1 s for the unpacked app. `JoltDesk.exe` from the zip is the real app, so taskbar pinning needs no relaunch workaround. The portable relaunch code in `desktop.cjs` stays for anyone still running an old portable exe. To zip an existing unpacked build, use `electron-builder --win zip --arm64 --prepackaged <dir>/win-arm64-unpacked`.
- Prompt-cache stability for local providers (`BOLT_STABLE_TOOLS=1` when `profile.provider==='local'`): `approval.ts` declares the full tool set in a fixed order (`declared()`). It keeps the system prompt identical, with a fixed `<bolt_permissions>` text, and appends the changing `<bolt_permission_state>` (mode and allowed tools) to the end of the last payload message only. Only the tail differs between requests. Enforcement happens in `tool_call` through `allowed()`, and blocked calls get a reason that names the mode and Web state. Cloud providers keep the previous per-mode tool list and system notice. A full reprocess of a ~32K chat took the user 14 minutes on a laptop CPU, at about 37 tokens/s.
- Lean prompt (measured with `work/prompt-size-probe.mjs`, Bypass with Web, 17 tools): the system prompt dropped from about 1,209 to 805 tokens, because `rewrite()` strips Pi's `<docs>` pointers, and the tool definitions from about 2,593 to 1,863 tokens. `COMPACT_TOOLS` and `compactTool()` in `approval.ts` give built-in tools shorter fixed wording that keeps the 2000-line/50KB limits, offset/limit paging, and edit uniqueness rules. The browser tool text was shortened too. A new Chat-only chat sends 0 tools.
- Declared tools per chat only grow. `declaredMode`/`declaredWeb` in `approval.ts` is a high-water mark of mode (chat < read < ask/bypass) and Web. It is reported in `BOLT_STATE`, saved on the chat as `chat.declaredMode`/`chat.declaredWeb`, and passed back as `BOLT_DECLARED_MODE`/`BOLT_DECLARED_WEB`, so a restarted engine declares the same set. Raising permissions changes the prefix once. Lowering never does.
- Screenshots while hidden: the user's agent got "browser is hidden" from `browser_screenshot` while JoltDesk was in the background. Hidden windows run no `requestAnimationFrame`, so `browser-panel.mjs` `sync()` uses `setTimeout` when `document.hidden`. `capturePage()` never settles for a view that is not on a window, so `browser-agent.cjs` caps it at 3 s. An empty or timed-out capture calls `forceShow(tab)` in `browser-pane.cjs`, which re-attaches at the last bounds or the right part of the window, then retries. A CDP `Page.captureScreenshot` fallback was tried and dropped, because attaching `webContents.debugger` broke the Playwright-driven app.
- Image parts of tool results, such as screenshots, are drawn with `showToolImages()` in `app.js`, both live and from history. Before, they rendered as an empty box.
- Context meter during agent runs: each step starts a reply with empty usage. `updateMetrics` prefers the server's `prompt_progress` total (`promptTotal`, reset at `generation_start`), then live usage, then the previous assistant message's input + cacheRead + cacheWrite + output, so the meter no longer drops to zero between tool steps. Session usage already matched llama.cpp (input = prompt_n, cacheRead = cache_n).
- Terminal tab: `refresh()` holds socket events while it loads the snapshot (`held`), then replays them on top. Otherwise a command started during the load was wiped by the older snapshot.
- The model switch in `app.js` (`confirmModelSwitch`) warns before moving a chat of 4,000 tokens or more to another local model. Prefill speed per model is stored in localStorage as `joltdesk-prefill:<connectionId>::<modelId>`, taken from `replyMetrics.serverTimings.prompt_per_second` when `prompt_n` is at least 500. `confirmAction()` is a reusable confirmation dialog (`#confirm-dialog`).
- Command tools (`bash`, `powershell`) are recorded only as "commands ran". Their file effects are not tracked.
- Keep the app’s MIT license separate from Pi-Bolt and other bundled notices. Preserve the signed engine bundle’s notices and provenance in distributions.

## Release convention

Keep generated binaries, private diagnostics, profiles, and engine downloads out of Git. Build the Windows ARM64 zip, smoke-test the package using an isolated profile, check the artifact and license files, and attach the executable to a versioned GitHub release.
